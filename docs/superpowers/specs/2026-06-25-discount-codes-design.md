# Design — Discount codes + reservation-only booking (v0.45.0)

## Context

On the public booking page `https://blackvoltmobility.com/book` ("Book your ride"),
two changes are needed:

1. **Remove the "Now" (on-demand) option.** Black Volt currently does not run
   on-demand rides — only reservations. The booking flow must always require a
   scheduled date/time.
2. **Add discount codes.** Customers can enter a discount code at booking time. The
   platform needs a way for drivers and admins to generate and manage these codes.

The driver requirement: each **driver** generates their **own** codes, redeemable only
by **their** clients — i.e. if Ender creates a code, redeeming it ties the ride to
Ender. Drivers set the **usage limit**, **expiry date**, and **discount %**. **Admins**
do everything a driver does, plus a module to create codes **for all drivers or selected
drivers** so each of those drivers can offer it to their own clients.

In the codebase, "a driver's clients" maps to **tenant scoping**: every `Client`,
`Ride`, and `RateConfig` row carries `tenant_id`, and a driver's `AllowedUser.tenant_id`
identifies their tenant. There is no per-client→driver link beyond the tenant, so the
**discount code itself is the binding**: it is owned by a tenant (driver), and redeeming
it attributes the ride to that tenant.

**Expected outcome:** `/book` is reservation-only; customers can apply a discount code
that lowers the fare and routes the ride to the driver who owns the code; drivers manage
their own codes in a new dashboard module; admins additionally run multi-driver campaigns.

## Decisions (confirmed with the user)

- **Redemption model:** single public `/book`; the entered code is looked up globally and
  identifies its owning driver.
- **Attribution = full handoff:** a redeemed driver code creates the ride in that
  **driver's tenant**; the driver sees and manages it in their own dashboard (passenger
  name/phone carried on the ride; `client_id` null).
- **Code format:** the creator may **type a custom code** (e.g. `ENDER10`) **or** press
  **Generate** for a random one (e.g. `BV-7K2QX9`). Stored uppercase, unique globally.
- **No stacking:** if a discount code applies, the existing loyalty discount is **not**
  also applied (the code replaces it).
- **Discount cap:** drivers may set **1–50%**; admins **1–100%**.
- **Admin multi-driver = campaign:** the admin defines a campaign (name, %, max uses,
  expiry) and picks drivers (all or selected); the system generates **one code per
  driver** (e.g. `SUMMER25-ENDER`, `SUMMER25-TOBIAS`), each attributed to that driver and
  linked to the campaign.

## Data model

New tables (Alembic migration `0027_discount_codes`, `down_revision =
"0026_ride_preferences_snapshot"`):

### `discount_codes`
| column | type | notes |
|---|---|---|
| `id` | PK | |
| `tenant_id` | FK → tenants | owning driver; redemptions attribute here |
| `code` | str, unique (global) | stored UPPERCASE; case-insensitive lookup |
| `discount_pct` | float | 1–100 (≤50 enforced for driver-created) |
| `max_uses` | int | required |
| `used_count` | int | default 0 |
| `expires_at` | date/datetime | required; the "fecha límite" |
| `active` | bool | default true (soft disable) |
| `created_by_email` | str | who created it |
| `campaign_id` | FK → discount_campaigns, nullable | set when generated by an admin campaign |
| `created_at` | datetime | |

### `discount_campaigns` (admin)
`id`, `name`, `discount_pct`, `max_uses`, `expires_at`, `created_by_email`, `created_at`.
Groups the per-driver codes an admin generates.

### `rides` (extend existing model)
Add `discount_code_id` (FK → discount_codes, nullable) and `discount_amount` (float,
default 0) — the snapshot of what was applied.

## Approach

### Backend (TDD: Red-Green-Refactor)

- **Models:** `backend/app/models/discount.py` (`DiscountCode`, `DiscountCampaign`),
  re-exported from `backend/app/models/__init__.py` so Alembic autogenerate sees them.
  Wrap any str-enum with `pg_enum()` from `app/db/base.py`. Add the two columns to
  `backend/app/models/ride.py`.
- **Service:** `backend/app/services/discounts.py` — pure-ish functions:
  - `create_code(db, tenant_id, is_admin, payload)` — validates `%` cap (≤50 unless
    admin), uppercases/uniqueness-checks the code, generates a random one if none given.
  - `list_codes(db, tenant_id)` / `set_active` / `delete_code` — tenant-scoped.
  - `validate_code(db, code)` — **global** lookup; returns the code row if active, not
    expired, and `used_count < max_uses`; else a typed rejection reason.
  - `create_campaign(db, payload, driver_tenant_ids)` — creates the campaign + one
    `DiscountCode` per driver tenant (`{BASE}-{driver_suffix}`), all linked to it.
- **Pricing:** in `backend/app/services/pricing.py`, add a `discount_code_pct` path that
  appends a `{"label": "discount_code", "amount": -x, "pct": ...}` line (mirroring the
  existing `loyalty_discount` block at ~lines 102-107) and subtracts from total. When a
  code applies, **skip** the loyalty discount (no stacking).
- **Booking integration:** `backend/app/services/booking.py:create_ride` accepts an
  optional `discount_code` (and `build_quote` an optional pct for preview). On a valid
  code: apply the discount to the fare snapshot, set `ride.tenant_id = code.tenant_id`
  (handoff), `client_id = null`, copy `passenger_name/phone`, set
  `discount_code_id`/`discount_amount`, and increment `used_count` atomically.
- **API routers:**
  - `backend/app/api/v1/discounts.py` (`prefix="/discounts"`):
    - `require_staff` + `resolve_tenant_id`: `GET ""` (list own), `POST ""` (create),
      `PATCH /{id}` (active toggle), `DELETE /{id}`.
    - `POST /validate` (`require_auth`): `{code}` → `{valid, discount_pct}` or rejection.
    - `POST /campaigns` (`require_admin`): create campaign → per-driver codes;
      `GET /campaigns` to list. Driver list reused from the Team/AllowedUser source.
  - `backend/app/api/v1/rides.py`: `RideCreate`/`QuoteRequest` gain `discount_code: str |
    None`; `create_ride`/`post_quote` thread it through. Mount the new router in
    `backend/app/main.py`.
- **Tests** (`backend/tests/test_discounts.py`, + booking/quote test additions):
  expired/exhausted/inactive code → rejected; driver `%` > 50 → 422, admin > 50 → ok;
  custom-vs-generated code creation + global uniqueness collision; `validate` global
  lookup; handoff (ride lands in the code's tenant, `client_id` null, passenger carried);
  no-stacking (loyalty skipped when code applied); `used_count` increments and blocks at
  `max_uses`; campaign generates N codes (one per selected driver) linked to it.

### Frontend

- **`/book`** (`frontend/components/bv/web/Booking.tsx`): remove the Now/Schedule toggle
  (lines ~254-281); force reservation mode (always render the date/time block, date
  required to proceed). Add a **discount code** input + "Aplicar" in the review/quote
  step; on apply, call `validateDiscount(code)` and re-quote with the pct, showing the
  `-X%` line and discounted total (or an inline error). Thread `discount_code` into the
  `createRide` payload. Types/client in `frontend/lib/booking.ts`.
- **Driver module** `frontend/components/bv/dash/Discounts.tsx` + route
  `frontend/app/dashboard/discounts/page.tsx` (mirror `Rates.tsx`/`Team.tsx`): list own
  codes; create form (code field with **Generate** button, %, max uses, expiry);
  activate/deactivate; delete. Optimistic where sensible.
- **Admin section** (same page, gated by `me.is_admin`): "Campaign" form — name, %, max
  uses, expiry, driver picker (all / selected, from the team list) → `POST
  /discounts/campaigns`; show generated codes.
- **Nav:** add `discounts` to `DashShell.tsx` `NAV` **and** `DriverTabBar.tsx` `MORE`
  (driver-scoped, not admin-only). Titles via `dash.title.discounts`.
- **i18n:** EN + ES keys for `/book` code field, the module, nav/title, and validation
  messages, in `frontend/lib/i18n.tsx`.
- **Version:** `frontend/lib/version.ts` → **0.45.0** + `CHANGELOG.md` entry.

### Out of scope (YAGNI)

## Security notes (for the security-review before deploy)

- **All validation server-side:** `%` cap (≤50 driver), `max_uses`/expiry/active checks,
  uniqueness — never trust the client.
- **Tenant scoping:** driver code management (`/discounts` CRUD) scoped via
  `resolve_tenant_id`; a driver can only see/modify their own codes. `POST /validate` is
  intentionally **global** (public booking) but returns only `{valid, discount_pct}` — no
  tenant/owner data leaked.
- **Admin-only campaigns:** `POST /discounts/campaigns` guarded by `require_admin`
  (re-checked against DB, per `session_is_admin()`), and the `%` cap is bypassed only for
  admins.
- **Atomic redemption:** increment `used_count` and re-check `< max_uses` in the same
  transaction to prevent over-redemption.
- **Handoff integrity:** reassigning `ride.tenant_id` to the code's tenant must not leak a
  tenant-1 `client_id` into another tenant — set `client_id = null` and carry
  passenger name/phone on the ride.
